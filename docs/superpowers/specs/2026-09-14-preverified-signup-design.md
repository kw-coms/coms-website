# 이메일 사전 인증 가입 및 관리자 회원 추가 설계

## 목표

일반 회원은 이메일 인증에 성공한 순간에만 `members`에 생성한다. 회장은 회원 관리 화면에서 이메일 인증 없이 회원을 직접 추가할 수 있다. 현재 남아 있는 이메일 미인증 회원은 기존 회원 삭제 정리 경로로 제거한다.

## 유지할 계약

- 브라우저에 캐시된 기존 가입 화면을 위해 `POST /api/auth/signup` → 코드 입력 → `POST /api/auth/email-verification/confirm-signup` 순서와 응답 필드는 유지한다.
- 명부 검증, 금지 학번, 전화번호 일치, 기수, 준회원 초기 역할 규칙은 그대로 적용한다.
- 가입 비밀번호는 모든 단계에서 평문으로 저장하지 않는다.
- 인증 전 데이터는 회원 목록, 로그인, 권한, 알림, 작성자 검색에 나타나지 않는다.
- 관리자 회원 추가는 회장만 가능하며 감사로그를 남긴다.

## 데이터 모델

`V92__pending_signups.sql`에서 `pending_signups`를 추가한다.

- `id UUID PRIMARY KEY`: 서버가 생성하는 내부 식별자
- `eligible_member_id BIGINT NOT NULL`: 검증된 명부 행
- `student_id VARCHAR(64) NOT NULL`: 재학생 학번 또는 졸업생용 결정적 `G연도-명부ID`
- `name`, `email`, `password_hash`, `department`, `generation`, `phone`, `aspiration`, `interests`, `signup_type`, `initial_role`: 최종 회원 생성에 필요한 정규화된 값
- `verification_code_hash`, `code_expires_at`, `verification_attempts`: 10분짜리 코드와 최대 5회 검증
- `created_at`, `expires_at`: 임시 가입은 24시간 뒤 만료
- `student_id`와 `lower(email)`에 고유 인덱스, `expires_at`에 정리 인덱스

비밀번호와 인증코드는 BCrypt 해시만 저장한다. 원본 비밀번호·인증코드는 저장하지 않는다. 이메일은 로그인 식별자이므로 pending 단계에서도 대소문자 무시 고유성을 보장한다.

## 일반 가입 흐름

### 가입 시작

`POST /api/auth/signup`은 기존과 같은 `SignupRequest`를 받는다.

1. IP 제한, 요청값, 명부, 금지 학번, 전화번호, 기존 회원·이메일 중복을 검증한다.
2. 졸업생 `G연도-명부ID`는 계산만 하고 명부에는 아직 쓰지 않는다.
3. 비밀번호와 인증코드를 BCrypt로 해시한다.
4. 같은 학번의 기존 pending 행을 잠그고 최신 폼 값으로 갱신한다. 이메일이 다른 pending/회원에 사용 중이면 거부한다.
5. 인증 메일을 전송하고 기존 `AuthResponse` 형태로 학생 식별자를 반환한다. `members`는 만들지 않는다.

pending 행을 먼저 커밋한 뒤 메일을 전송한다. 메일 전송이 실패하면 별도 트랜잭션으로 해당 pending 행을 제거하고 `503`을 반환한다. SMTP 성공과 DB 커밋은 원자적으로 묶을 수 없으므로, 응답 유실 시 사용자가 재전송할 수 있게 한다. 같은 학번 재요청은 1분 쿨다운 이후 가능하며 입력한 이메일을 수정할 수 있다.

### 재전송

`POST /api/auth/email-verification/request-signup`은 pending 행을 조회해 코드를 교체한다. 계정 존재 여부를 노출하지 않는 현재 고정 응답과 IP 제한을 유지한다. 배포 직전 생성된 레거시 미인증 회원은 운영 정리 후 0명이므로 레거시 fallback은 두지 않는다.

### 인증 완료

`POST /api/auth/email-verification/confirm-signup`은 pending 행을 비관적 잠금한다.

1. 만료·시도 횟수·코드를 확인한다.
2. 금지 학번, 명부 행, 회원 학번·이메일 중복을 다시 검증한다.
3. 졸업생이면 이 시점에 명부의 생성 학번을 확정한다.
4. `email_verified=true` 회원을 생성한다.
5. pending 행을 삭제하고 감사로그를 기록한다.

회원 생성과 pending 삭제는 한 트랜잭션이다. 두 번 확인 요청이 동시에 들어와도 회원은 하나만 생성된다.

## 만료 정리

기존 일일 보존 작업에 `expires_at < now()`인 pending 행 삭제를 추가한다. 조회 시에도 만료 행을 즉시 삭제한 것으로 취급한다. pending 데이터에는 개인 정보가 있으므로 보존 기간을 늘리지 않는다.

## 회장 전용 회원 추가

`POST /api/admin/members`를 추가한다. 요청값은 학번, 이름, 이메일, 초기 비밀번호, 기수, 역할, 선택적 학과·전화번호다.

- `ADMIN`만 호출 가능하며 서비스에서도 다시 확인한다.
- 학번은 현재 학생 계정 규칙인 숫자 10자리로 제한한다.
- 역할은 `ASSOCIATE`, `USER`, `OFFICER`, `VICE_PRESIDENT` 중 선택한다. 새 회장 생성은 기존 역할 변경 절차로만 가능하게 해 실수를 줄인다.
- 이메일은 인증 완료 상태로 생성한다.
- 명부 행이 없으면 함께 추가한다. 같은 학번에 다른 이름의 명부 행이 있으면 `409`로 멈추며 덮어쓰지 않는다.
- 명부와 회원 생성은 한 트랜잭션이다.
- 초기 비밀번호는 기존 관리자 비밀번호 초기화와 동일하게 공백이 아닌 값을 허용한다. `1234` 같은 임시 비밀번호도 가능하며, 폼에서 최초 로그인 후 변경 안내를 표시한다.
- 감사로그에는 학번·역할만 남기고 비밀번호·전화·이메일 원문은 남기지 않는다.

웹 `회원 관리` 탭 상단에 `회원 추가` 버튼과 접이식 폼을 둔다. 저장 후 목록을 다시 불러오고 생성된 회원을 표시한다. 마지막 회장 보호, 역할 변경, 삭제, 비밀번호 초기화 기능은 그대로 유지한다.

## 기존 미인증 회원 정리

배포 전 현재 미인증 회원을 다시 조회한다. 사용자가 승인한 전체 대상을 기존 `AdminService.deleteMember`와 동일한 purge 순서로 삭제하고 감사로그를 남긴다. 삭제 대상 수와 마스킹된 식별자를 실행 직전·직후 기록한다. 인증 완료 회원은 절대 포함하지 않는다.

## 오류 처리

- 메일 실패: `503`, 방금 만든 pending을 별도 트랜잭션으로 제거
- 코드 만료·오류: `400`, 최대 5회 후 코드 제거
- pending 만료: `404` 대신 동일한 `400` 안내로 계정 존재 여부를 감춘다
- 학번·이메일 동시 가입 경쟁: DB 고유 제약과 비관적 잠금으로 한 요청만 성공
- 오래된 가입 화면에서 인증 전 로그인: 회원 행이 없으므로 로그인 실패가 정상
- 관리자 중복 추가: `409`, 기존 행 변경 없음

## 테스트

- `/signup` 후 회원이 없고 pending만 존재하며 로그인할 수 없음
- 올바른 코드 확인 후 회원 1개 생성, pending 삭제, 이메일 인증 완료
- 잘못된 코드 5회, 만료, 재전송, 메일 실패 롤백
- 동시 확인·동시 가입에서 중복 회원 없음
- 졸업생 학번은 인증 전 명부 미변경, 인증 후 확정
- pending 만료 정리
- 관리자 생성의 권한 경계, 명부 동시 생성, 충돌 롤백, 역할 제한, 감사로그 마스킹
- PostgreSQL에서 V92 전체 마이그레이션 실행
- 웹 가입/관리자 회원 추가 스모크 및 접근성 테스트

## 배포 순서

1. 현재 미인증 대상 스냅샷 확인
2. 코드 PR의 H2·PostgreSQL·프론트·실백엔드 E2E 통과
3. PR 머지 및 V92 배포
4. 일반 가입 테스트 계정으로 인증 전 로그인 실패와 인증 후 생성 확인
5. 현재 미인증 회원을 기존 purge 경로로 삭제
6. 회원 관리에서 관리자 직접 추가 테스트 후 즉시 테스트 계정 삭제

## 비목표

- 소셜 로그인, 이메일 링크 인증, SMS 인증은 추가하지 않는다.
- 회원 앱에는 가입 화면이 없으므로 변경하지 않는다.
- 기존 인증 완료 회원의 로그인·세션·비밀번호는 변경하지 않는다.
